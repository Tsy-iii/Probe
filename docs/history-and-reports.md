# 历史查询、重新执行与报告证据

> 当前入口见 [主 README](../README.md)；文末旧验收数字和截图为有日期的历史记录，不代表当前服务状态。`.local/` 与 `test-results/` 仅为运行产物位置，历史原始文件不随仓库发布。

当前入口：http://127.0.0.1:5174。此增量补全“找到过去的任务 → 再次执行 → 对应原记录 → 查看与导出证据”，GitHub Actions 继续后置。

## 报告链接与失败定位

点击任务摘要里的「报告链接」，复制 `http://127.0.0.1:5174/?run=任务UUID`，在本机另一标签页直接打开该报告。刷新保留当前任务和报告／pytest 日志标签；浏览器前进、后退恢复对应任务。链接只读取已有任务，不提交测试，不冻结源码版本。特定尝试及 HTTP 服务日志仍从执行详情选择。

左侧套件控制下一次提交，右侧展示已打开的历史任务。二者不同时，摘要明确显示正在查看的报告套件与待执行套件；「切换到报告套件」只改变套件选择，勾选范围继续按左侧设置，精确复用原任务范围仍使用「重新执行」。

报告里的「定位首个失败」会清除报告搜索和结果筛选，展开第一个失败／错误用例并定位到它。「展开可见用例」「收起可见用例」只改变当前显示的用例，隐藏用例的展开状态与报告计数保持不变。每条用例的「复制命令」复制完整用例 ID 对应的 `.venv/bin/python -m pytest ... --require-postgres -v`；在 Probe 根目录运行当前磁盘代码。缺少完整 ID 的旧报告不能猜测执行范围，按钮禁用；剪贴板不可用时展示可手动复制的命令。

失效任务链接显示明确错误与「查看最近任务」，停止反复读取不存在的记录；格式错误的任务参数回到默认工作台，不向 API 发送非法路径。该增量前端构建与 10 项浏览器检查通过，记录在 `.local/browser-check/report-tools-results.json`。复制的单条命令用 `--collect-only` 实际收集到 1 条用例，未执行新的业务测试。37 个任务及演示数据前后核对一致。

## 一条体验流程

1. 在「执行历史」搜索框输入任务 ID 的前几位、套件 ID 或中文套件名称，等待搜索更新。搜索框旁点击「筛选」，选择套件与执行状态，再点击「收起筛选」。右上角数字表示符合条件的任务数；顶部累计任务与通过／失败统计仍是全局数据。
2. 点击历史底部箭头翻页，每页 10 条。没有匹配记录时显示明确的空结果；搜索框旁的 × 清除搜索及两个筛选条件。搜索与分页固定，记录在中间滚动，套件列表不随筛选展开被压缩。
3. 打开一条已结束的任务，点击右上「重新执行」。这会创建新的任务 ID，复用原任务超时与保存的用例 ID；新任务摘要显示「来自 #原ID」，执行详情抽屉显示完整来源。点击来源链接可以回到原报告。原任务的状态、时间、计数、报告和尝试记录保持不变。
4. 点击左侧「重放上次提交」。如果上一次是重新执行，它会重放那次重新执行请求，返回刚才的新任务，不创建第三个任务。每次明确点击「重新执行」会使用新提交键；响应不确定时，未确认的提交键会保存在浏览器会话中。
5. 选「金额计算故障对照」的失败历史，在报告中点击「失败 / 错误」。用例列表只显示失败与错误，但上方总计仍来自完整报告。可以搜索函数名、中文业务标题或源码文件，再点击「显示全部用例」恢复。
6. 点击「证据 JSON」，下载整个任务的执行参数、选择、来源关系、尝试、报告、请求／数据库证据和日志。页面筛选不裁剪导出的原报告。没有完整报告的超时、取消或执行异常也可以导出已有记录，报告与未知计数保持 null。

历史筛选可能隐藏当前选中的任务。详情仍独立跟踪该任务，执行结束后会更新；提示中的「在历史中定位」会清除套件／状态条件并按完整任务 ID 查找。

自动刷新与主动翻页分开处理：两秒一次的后台读取保留当前页码、列表和翻页按钮状态，不反复显示「读取中」。主动搜索、筛选或翻页仍有读取状态，并取消旧请求；后台轮询不会中断尚未完成的读取。

结果区现在以紧凑摘要展示任务名称、ID、范围、耗时与退出码。点击「执行详情」查看完整上下文、选择及执行尝试；点击某次尝试进入日志。点击「专注结果」隐藏左栏和全局统计，扩大报告／日志的可见区域；点击「返回工作台布局」或按 Esc 恢复。抽屉打开时 Esc 先关闭抽屉。

失败用例优先展示红色「pytest 用例失败」与原始失败消息，再展示请求证据；展开「原始 pytest 断言与堆栈」可查看完整错误。证据表只包含开发者明确采集的检查项，绿色「符合」表示该项期望与实际一致，最终用例状态仍来自 pytest。一条用例可能在请求成功后、后续断言处失败；没有详细错误时明确提示查看日志，不显示成跳过或通过。

真实学习任务 `59adacf5` 展示了这个区别：HTTP 创建订单的数量为 3、总金额为 5970 分，四项采集检查都相符；测试第 27 行仍断言数量为 2，因此 pytest 记录 `assert (3 == 2)`，结果是 0 通过、1 失败，查询与支付步骤尚未执行。前端构建和 5 项报告显示检查通过，旧报告的失败信息、采集数据和用户源码未修改，也没有重新执行该业务用例。记录在 `.local/browser-check/report-failure-clarity-results.json`。

失败断言能唯一关联到请求字段时，直接显示在请求表的对应行：该任务的 `quantity` 显示期望 2、实际 3、不符，来源为「pytest 失败断言」。其余行注明「采集配置」，不把这些对照当成全部断言已通过。「原始采集检查」保留当次的 3 / 3 值；原始证据与 JUnit 不修改。已关联的断言不重复显示独立数值表，无法关联的失败仍保留在红色失败区域。

`frontend/src/assertionFailure.ts` 仅从已保存的 pytest 失败文本及其中的原始断言行提取可明确对应的整数相等比较，不读取最新源码来解释过去的任务。变量期望、反向表达式、重复预期、算术表达式、大整数或其他无法确定的错误继续展示原始失败信息，不推测字段和数值。前端构建通过；真实旧报告、窄屏布局及模拟的组合断言／歧义场景共 12 项页面检查通过。35 个任务和用户测试源码保持一致，记录在 `.local/browser-check/assertion-comparison-results.json`。

请求表关联依据是字段名、断言实际值与已保存响应内容能唯一对应。多个请求或多个比较都能匹配、实际值不一致、字段不同的情况不强行关联。对应 7 项页面检查通过，包含真实 `quantity` 失败行、原始检查展示、窄屏和模拟歧义场景；既有任务、报告和用户测试源码保持一致，记录在 `.local/browser-check/linked-request-assertion-results.json`。

提交、重新执行和重放的成功反馈显示在右下角独立浮层中，不占套件卡片高度。提示 8 秒后自动关闭，鼠标悬停或键盘聚焦时暂停计时，也可以手动关闭。每次重放都会重新显示提示，历史记录中的任务状态继续独立更新。

常规桌面窗口中，套件列表按五条完整行分配高度，滚动停在条目边界；九个套件仍都可以通过列表滚动选择。历史区域按两条记录所需空间分配，避免条目被截断，也不再加高整页。图表套件、比较范围和历史筛选共用深色下拉菜单，支持方向键、Home／End、Enter、Esc 和 Tab；菜单通过页面浮层展示，避开卡片裁切。实现位于 `frontend/src/WorkbenchSelect.tsx`。

比较边界：

- 每个套件只读取最新 100 个任务，组内最多显示 20 次。页脚明确标出已读取数和套件总数；某组更早的记录可能不在图表中，不能把这个样本当成全部历史统计。
- 分组使用排序后的精确用例 ID。同一组 ID 的全选和手选可以归为一组；数量相同但 ID 不同的两组不会合并。
- 旧任务没有选择快照时进入「旧记录 · 范围未保存」，并提示无法确认执行范围相同，不补造过去的选择。
- 用例 ID 相同不代表代码、配置或测试环境相同，平台目前没有冻结这些版本。因此图表展示执行结果变化，不自动声称某次版本更新造成了失败。
- 四类计数与总计完整且一致时才画柱高。未知计数保持未知，正常生成的零计数与缺失报告分开展示。任务取消、超时或执行异常可能带有部分报告，不能用部分通过宣称全部通过。
- 每个柱子对应任务保存的结果。Worker 内部尝试不会另画成多个任务，重放提交也不新增柱子；主动重新执行会创建新任务，因此可以产生新的柱子。

键盘用户可以用 Tab 聚焦柱子查看提示，Enter 打开报告，Esc 关闭提示。查询失败时展示明确错误与「重新读取」按钮，图表不会继续展示另一个套件的旧柱子。

## 重新执行与重放的区别

| 操作 | 任务 ID | 是否执行 pytest | 用途 |
| --- | --- | --- | --- |
| 提交测试任务 | 新 ID | 是 | 使用左侧当前套件与选择运行新测试 |
| 重新执行 | 新 ID，关联原任务 | 是 | 复用原任务范围和超时，再验证当前代码 |
| 重放上次提交 | 返回该次请求已创建的 ID | 不新增执行 | 请求响应不确定时去重，或验证幂等 |

重新执行不会把失败的旧任务改成通过，也不会增加旧任务的 Worker 尝试次数。Worker 异常恢复仍是原任务内部的独立尝试，两种关系分别记录。

新任务有选择记录时，重新执行使用原来保存的精确用例 ID。用例后来被删除或不再属于套件时返回 422，不能扩大成整套执行。旧任务没有选择记录时，明确采用“当前套件全部”，旧记录仍保持空值，不补造过去的选择。执行使用当前磁盘代码，没有冻结源码版本。

## 接口

历史查询：

```text
GET /api/runs?limit=10&offset=0&suite_id=contract&status=failed&q=任务ID或套件名称
```

`limit` 为 1～100，`offset` 为 0～1000000；套件与状态必须是已有枚举，搜索最多 100 字符。结果包含：

- `items`：当前页。
- `matched_total`：当前搜索与筛选的匹配数。
- `total`、`summary`：全局任务数量与状态统计。
- `limit`、`offset`：当前分页位置。

搜索是字面量匹配，`%`、`_` 不会被当成 SQL 通配符。查询由 SQLAlchemy 绑定参数生成。列表、匹配数、全局统计在同一个 PostgreSQL 只读快照中读取，列表不加载完整报告 JSONB。

重新执行：

```bash
curl -i -X POST http://127.0.0.1:8001/api/runs/替换成原任务完整ID/rerun \
  -H 'Idempotency-Key: learn-rerun-001'
```

原任务必须已结束。不提供覆盖参数；传入未声明的请求体字段返回 422。首次返回 202；相同提交键重放返回 200，沿用原先创建的新任务 ID。一个提交键不能用于不同来源任务或混用于普通提交。

证据下载：`GET /api/runs/任务完整ID/evidence`。任务结束后返回附件 JSON，包含 `schema_version`、实际导出时间、任务详情和日志。导出使用已保存的报告，不推测根因或补造缺失证据。执行日志最多导出最后 256 KiB，并保留 `truncated` 标识；文件不存在时内容为空。原始 JUnit 下载继续保留。

## 关键实现与取舍

`probe/platform/repository.py` 在 PostgreSQL 中筛选与分页，区分匹配数量和全局统计。按创建时间降序、再按 ID 降序确定顺序。当前采用 offset 分页，适合个人项目规模；翻页期间出现新任务或刷新后，记录位置可能移动，不宣称是冻结的历史列表。

`test_runs.rerun_of_id` 是可空自引用外键，记录新任务来自哪个原任务。迁移 `0004_rerun_source` 只增加此字段与约束，原任务保持空值。创建与去重继续使用事务和唯一提交键，指纹包含来源 ID，避免混淆重新执行与普通提交。

`probe/platform/main.py` 复用已有选择校验和任务创建逻辑，增加重新执行及证据导出。API 不执行测试，仍由独立 Worker 领取新任务。

`frontend/src/App.tsx` 分别管理历史请求与详情请求。改变筛选时取消旧列表请求，防止迟到结果覆盖新条件；详情根据自身返回的状态继续读取，直到任务结束，避免因任务不在当前页而停止更新。浏览器会话中的提交记录同时支持普通提交和重新执行，重放会调用正确的入口。

`frontend/src/RunReport.tsx` 在已读取报告上做展示筛选，用例结果和完整计数不变；有选择快照时展示保存的中文标题与真实函数名。超时、取消或执行异常携带部分报告时，页面明确说明部分通过不能代表全部执行完成。
