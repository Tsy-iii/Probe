## 2. 在 Swagger 创建订单 A：买两件

1. 切到订单文档，找到绿色的 `POST /orders`，点击展开。
2. 点击右侧 `Try it out`，这时请求体变为可以编辑。
3. 将请求体完整替换为下面的 JSON。
4. 点击蓝色 `Execute` 一次。
5. 看下方 `Server response` 内的 `Code` 和 `Response body`，这是本次真实响应；静态的 `Example Value` 只是接口示例。

```json
{"product_id":1,"quantity":2}
```

预期 HTTP `201`，响应包含 `id`、`product_id:1`、`quantity:2`、`total_amount_cents:3980`、`status:"pending"`。复制 `id` 的完整 UUID 字符串，命名为「订单 A」，不要只复制前八位。

每点击一次创建请求都会创建一个新订单。创建订单接口当前没有提交键去重；只有接下来的支付回调和平台任务提交有各自的幂等机制。

回数据页刷新，点击「订单 orders」并清除筛选：订单 A 应出现，订单总数增加 1；点击订单 A 看记录详情中的关联信息，商品 1 库存从 7 变为 5，金额 39.80 元，支付事件数仍为 0。创建时已经扣库存，但尚未支付。

## 3. 通过查询接口读取订单 A

Swagger 中展开蓝色 `GET /orders/{order_id}` → `Try it out` → 在 `order_id` 输入框粘贴 A 的完整 ID → `Execute`。

预期 HTTP `200`，返回 A 的数量 2、金额 3980 分、状态 pending。刷新数据页，库存与记录数应不变。GET 查询不会新增订单。

## 4. 先发一个金额错误的支付回调

Swagger 中展开绿色 `POST /payments/callback` → `Try it out`。将下面的 `替换成订单A的完整ID` 替换为实际 ID，其他字段照填。事件 ID 是这次支付通知的稳定编号，本流程用 `walkthrough-pay-20261109-01`；再次从头体验时请换一个新编号，避免与已存在的不同订单冲突。

```json
{
  "event_id":"walkthrough-pay-20261109-01",
  "order_id":"替换成订单A的完整ID",
  "amount_cents":1
}
```

点击 Execute，预期 `409`，`error.code` 为 `payment_amount_mismatch`。订单仍为 pending，库存仍为 5，支付事件仍为 0。刷新数据页核对。

这里的 1 是合法正整数，所以参数校验通过，随后业务规则拒绝金额不匹配。在事务里临时插入的事件也应回滚，不能留下“成功支付事件”。

## 5. 正确支付，再重复同一回调

在上一步的请求体中，只把 `amount_cents` 从 1 改为 3980，其他字段保持不变，再 Execute。

预期 `200`，支付响应结构为 `{"order":{...},"duplicate":false}`；状态在 `order.status` 中，应为 paid。数据页刷新后：订单 A 已支付，成功支付事件增加 1，商品库存仍为 5。点击 A 的「查看支付事件」，可以看到刚才的 event_id 与 order_id 关系。

保持整个请求体不变，再 Execute 一次：预期仍为 `200`，`duplicate:true`，订单仍为 paid，事件仍为 1，库存仍为 5。这就是同一事件重复送达时不重复变更业务。

再保持同一 event_id 和订单，只把金额改为 1990：预期 `409 event_conflict`，表示这个已成功登记的事件 ID 被携带不同内容重用。它和第一次的 payment_amount_mismatch 是两种不同错误。完成后把编辑框金额恢复为 3980，便于以后查看。

## 6. 验证已支付订单不能取消

展开 `POST /orders/{order_id}/cancel` → Try it out → order_id 填 A → Execute。

预期 `409 order_already_paid`。刷新后 A 仍为 paid，库存 5，事件 1。当前业务不支持支付后的退款与取消。

## 7. 创建订单 B，再取消两次

回到 `POST /orders`，请求体改为 `{"product_id":1,"quantity":1}`，Execute 一次，复制新 ID 为「订单 B」。预期 `201 pending`，金额 1990 分；刷新后库存从 5 变为 4，订单数再次增加 1。

在 `POST /orders/{order_id}/cancel` 的输入框中将 A 替换为 B，Execute：预期 `200 cancelled`，刷新后库存回到 5。

保持 B 的 ID，再 Execute 一次：仍为 `200 cancelled`，库存继续是 5，不能变成 6。重复取消成功只是返回已取消状态，不代表再次恢复库存。

再向支付接口发送 B 的迟到回调，使用一个新事件编号：

```json
{
  "event_id":"walkthrough-late-20261109-01",
  "order_id":"替换成订单B的完整ID",
  "amount_cents":1990
}
```

预期 `409 order_cancelled`。B 保持 cancelled，库存 5，支付事件总数仍是 1。按当前起点完成两笔订单后，演示库应有 6 个订单：pending 3、paid 1、cancelled 2。

## 8. 观察参数错误、库存不足和不存在

以下创建请求分别粘贴到 POST /orders 执行。一次只改变一个字段，每次都在真实 Server response 查看 HTTP 状态码。

| 请求体 | 预期 |
| --- | --- |
| `{"product_id":1,"quantity":0}` | 422 validation_error |
| `{"product_id":1,"quantity":-1}` | 422 validation_error |
| `{"product_id":999999,"quantity":1}` | 404 product_not_found |
| `{"product_id":1,"quantity":6}`，当前库存为 5 时 | 409 insufficient_stock |

如果实际库存不同，库存不足的请求数量填「当前库存 + 1」。失败后刷新，库存和订单数都不应变化。

查询接口的 order_id 可填合法但不存在的 `00000000-0000-0000-0000-000000000000`：预期 404 order_not_found。格式乱填的 ID 会先触发 422，不能用它验证“订单不存在”。

再看「订单演示数据」：刚才手动创建的 A/B 仍在，测试里的 5 件订单没有混入。因为测试用了 probe_test，而手动订单用了 probe。执行结束后临时 schema 被清理，所以测试历史数据要看保存的报告快照。

## 12. 重放同一次任务提交，观察平台去重

记下当前任务 ID 和累计任务数，在提交按钮旁点击圆形箭头按钮「重放上次提交」。它复用最近提交的套件、超时和提交键。

预期提示「已复用原任务」，任务 ID 与计数不变，不新增执行尝试。点击「执行详情」，在抽屉的「执行上下文」可以看到完整任务 ID 和提交键。

这里是“任务提交去重”；支付回调的 event_id 去重是另一个业务机制。修改测试代码后应点击「提交测试任务」创建新任务；重放不会重新运行修改后的代码。

## 13. 运行金额故障对照，练习失败定位

工作台选择「金额计算故障对照」，超时 60，提交新任务。预期状态「测试失败」，总计 2、通过 1、失败 1。

展开失败用例 `test_amount_with_faulty_implementation`：请求购买 2 件，HTTP 201，金额检查的期望是 3980，实际却是 1990。展开请求响应和数据库快照，可以看到响应金额与数据库金额都错了，因此需要检查金额计算／写入，不能归因于前端金额格式。

展开「原始 pytest 断言与堆栈」，看具体 assert 和实际值。页面上的「测试提供的定位提示」来自测试作者预先编写的说明，不是 AI 自动诊断。

再展开正确实现用例 `test_amount_with_correct_implementation`：同样购买 2 件，金额为 3980，断言通过。本套件只在隔离测试进程用 monkeypatch 制造错误，不修改正在运行的订单服务。

想观察固定 HTTP 错误，可再选择「固定错误演示」提交：测试显式开启故障注入，得到 503，却断言应该为 201，因此预期测试失败。这个场景在数据库访问前返回，不作为 PostgreSQL 事务证明。

## 14. 体验超时与取消

选择「慢执行演示」，将超时填 3，提交。它包含确定的 8 秒等待，因此预期「执行超时」。点击「执行详情」查看尝试与执行日志，确认停止原因和资源清理。没有完整报告时页面会说明无可读取报告，不能把它计为测试通过或断言失败。

再选同一套件，超时改为 30，点击提交新任务。看到「执行中」后立即点击右侧「取消任务」，观察「取消中 → 已取消」以及清理状态。如果太快而只看到最终状态，以实际记录为准。

如果任务尚在队列中就取消，它不产生执行尝试；如果等了超过正常等待时间而任务已完成，不能再取消这个已终结任务。要体验执行中取消，可以重新提交新任务并及时点击。这是重新体验不同操作时机，不是把失败重试成通过。

取消测试任务只是停止 pytest，不会把演示库的已支付订单 A 改成 cancelled。

## 16. 回到本地代码，直接运行同一个用例

打开 `tests/test_stock_boundary.py`，按「数据准备 → 请求 → 响应断言 → 数据库断言 → 库存耗尽后的请求」阅读。`tests/conftest.py` 准备真实独立测试库，`probe/service.py` 实现库存与金额业务，`probe/platform/runner.py` 注册套件并执行 pytest。

从项目根目录运行：

```bash
# Run from the repository root
source .venv/bin/activate
python -m pytest tests/test_stock_boundary.py --require-postgres -v
```

正常代码预期 1 passed。如果缺少数据库，--require-postgres 会使验证失败，而不是静默跳过。直接终端运行 pytest 不会向平台创建任务，所以工作台不会新增历史记录。

完整回归命令：`python -m pytest --require-postgres -q`。2026-11-09 补充用例选择功能后的最新实际结果为 73 passed、0 failed、0 skipped，1 条 TestClient 弃用提示；选择执行的体验与验证见 [用例目录与选择执行](case-selection.md)。金额故障与固定错误等演示不在默认测试集合中，由平台显式选择。
