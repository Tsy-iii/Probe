# 响应丢失：结果未确认，订单已经提交

这是确定性的受控传输实验：真实 PostgreSQL commit 成功后，ASGITransport 替身丢弃响应。它验证未知结果的处理，不声称复现了真实 TCP 网络分区。

## 两层响应必须分开

调用链为：测试客户端 → 平台 `/api/demo/orders` → 订单应用 → PostgreSQL。

订单应用已完成订单创建，但转发层未收到完整响应。平台捕获读取异常后向客户端返回 **504** 和“操作结果未确认”。这个 504 是平台生成的，不是订单服务返回的业务响应。

| 观察 | 本轮实际验证 |
| --- | --- |
| 平台 HTTP 状态 | 504 |
| 保存的上游业务响应 | `null`，未获得 |
| `outcome_unknown` | `true` |
| 库存 | 5 → 3 |
| 数据库订单数 | 0 → 1 |
| 支付事件数 | 0 |
| 实际创建请求数 | 1，没有自动重发 |

## 复现

```bash
.venv/bin/python -m pytest tests/platform/test_demo_orders.py::test_lost_reply_after_commit_is_unknown_and_not_retried --require-postgres -v
```

本轮通过。通过表示未知结果和数据库状态符合这项受控实验的断言，不表示实际创建请求收到了成功响应。

## 怎样制造丢失

[用例中的 LostReply](../../tests/platform/test_demo_orders.py) 先等待真实订单应用处理请求，再对 POST 抛出 `httpx.ReadTimeout`。因此测试明确知道故障在 commit 之后；就绪检查的 GET 仍然正常。

[平台转发代码](../../probe/platform/demo_orders.py) 不自动重试，只保留 `response=None` 和 `outcome_unknown=true`。用例在断言前采集数据库快照，并检查只有一次 `/orders` 创建调用。

## 定位顺序

1. 看响应来源：客户端收到的是平台的 504，上游响应为空。
2. 看异常阶段：实验在订单应用处理之后抛出读取异常，不能按“请求没发送”解释。
3. 查实际数据：库存减少、订单新增，说明本实验中的写入已经提交。
4. 查请求次数：只创建了一次，排除平台自动重试造成重复订单。

日志中的请求 ID 用于关联请求；它本身不是订单创建幂等键。

## 当前恢复策略

页面显示未确认状态，先查询订单和库存。[操作窗口](../../frontend/src/DemoOrderAction.tsx) 不允许在这次未知创建结果下直接重发；只读回库存也不会解除阻止。

这是交互保护，不是服务端创建幂等。关闭后重新打开表单仍可产生新订单，不能据此保证永不重复。并发环境中，库存减少或订单数增长不能单独证明属于哪一次请求，应结合订单记录、请求日志和实际业务标识核对。

模拟支付和取消已有各自的业务幂等规则；任务提交幂等也只针对测试任务，不能自动替代订单创建幂等。

## 尚未实现的保证

- 没有订单创建幂等键或创建请求到订单的持久映射。
- 没有自动对账、重试协调或跨服务事务。
- 不宣称外部支付／业务副作用的 exactly-once。
- 真实 TCP 读取超时另见 [HTTP 测试](../http-testing.md)；本例不能替代其网络验证范围。

面试展开点：为什么“超时”不等于“回滚”？客户端、转发层和数据库分别知道什么？需要哪种业务标识才能安全协调重发？
